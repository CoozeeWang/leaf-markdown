# Leaf 开发与仓库工作方式

这份说明供 Leaf 的开发者使用。公开产品仓库是 `CoozeeWang/leaf-markdown`，已进入 1.x 公开发行阶段。当前发行版本以 GitHub Releases 为准。

## 哪些资料放在哪里

- **公开产品仓库 `leaf-markdown`**：源码、正式测试、必要资源、依赖锁文件、构建和打包配置、面向开发者的现行文档。被 Git 跟踪的内容应可以公开。
- **私有工作资料**：个人研发记录、过程性方案、内部验收材料和可编辑工作副本不提交到本仓库。
- **只留在本机的生成物**：依赖目录、编译缓存、`dist/`、`test-results/`、日志和本地设置。用 `.gitignore` 排除，但忽略规则不会移除已提交的内容。
- **凭据**：密钥、签名证书、令牌和含真实凭据的 `.env` 不进入任何 Git 仓库。使用本机安全存储或托管平台的 secrets 设置。

`leaf-markdown` 是 Leaf 产品代码的主仓库。个人工作目录的名称和组织方式由各位开发者自行决定。

## 一项工作如何完成

1. 从最新的稳定 `main` 开一条功能或修复分支。一次分支围绕一个可解释的目标；需要隔离实验时另开分支。
2. 开工前查看 Git 状态，保护已有未提交修改。开发中可以保存 checkpoint commit，提交信息说明目前做到哪一步；一次对话不必对应一次 commit。
3. 功能完成后，按功能检查改动和暂存内容。源码、测试、文档、资源可以在同一功能提交中配套出现；无关改动分开提交。不把个人资料或构建产物顺手提交。
4. 运行与改动相称的检查。普通改动至少运行 `npm run check`；界面行为补跑相关浏览器测试；桌面文件、输入或平台行为补做相应原生检查。浏览器和构建通过不等于安装版验收。
5. 通过 PR 检查后合入 `main`。一串只为临时存档的 checkpoint 可 squash；几个独立且有追溯价值的提交可保留。不要为了整齐改写现有有价值的历史。
6. 合入后确认 `main` 的自动检查通过。需要安装包时按发布流程构建，不把安装包或缓存提交进源码。

`main` 应表示当前可构建、已通过约定检查的产品基线。紧急修复也在分支上完成并回到 `main`。对未完成的工作保留在分支，不让主线长期处于已知损坏状态。

## 版本号、内部构建与公开发行

- 日常修复、内部测试或本机安装不自动升级产品版本号。使用应用设置中的源码提交与构建时间区分同版本内部构建；测试包文件名包含提交号与平台。
- 准备下一次公开发行时，与上一发行版比较实际合入的改动，核对 macOS、Windows 和简中、台湾繁中、英文的验证范围。只有修复与兼容性改进时递增补丁号（例如 `1.0.4` → `1.0.5`）；增加向后兼容的功能时递增次版本号；有不兼容变更时评估主版本号并说明迁移影响。由维护者确定发布范围和版本号，不为每次提交逐次升版。
- 需要公开预览时使用 `X.Y.Z-beta.N`，同一目标版本每轮预览递增 `N`，并在 GitHub 标为预发布；正式发行使用不带预发布后缀的版本号。内部构建不等于公开预发布。
- 确定发布后、生成发布包前，同步更新 `package.json`、`package-lock.json`、`src-tauri/Cargo.toml`、`src-tauri/Cargo.lock` 和 `src-tauri/tauri.conf.json` 的产品版本号。同步 CHANGELOG、三语发布说明及 README／安装指南中的实际下载链接；说明按实际功能、修复及关联 Issue／PR 编写。
- 对外发布状态以 GitHub Releases 为准。已发布的版本号、标签和安装包不得用后续修复覆盖；下一轮发行使用新版本号。未合入的修改、仅制作过测试包的内容及尚未完成的人工验收不写成已发布或已验证。

## Issue 交付清单

创建或更新问题和需求时，以仓库对应的 Issue 模板为准；通过命令行或 API 创建也要包含模板中的交付进度和验证记录。提交前检查清单是否完整，并核对保存后渲染出的勾选状态。功能条件另列，不能代替交付清单。macOS、Windows 安装版验收分别记录，中文、英文覆盖范围写在各平台证据中；只有使用者明确确认才勾选相应安装版项。待验和延期保留未勾选状态；不适用须说明原因。关闭 Issue 不自动完成待验平台项。
