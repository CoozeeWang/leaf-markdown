# Leaf 开发与仓库工作方式

这份说明供 Leaf 维护者和协作 Agent 使用。它描述日常工作方式；公开仓库的建立与地址，须在开源准备检查完成后另行确定。

## 哪些资料放在哪里

- **产品仓库 Leaf**：源码、正式测试、必要资源、依赖锁文件、构建和打包配置、面向开发者的现行文档。被 Git 跟踪的内容原则上应可以公开。
- **私有工作空间 Leaf-work**：个人研发记录、过程性方案、内部验收材料和可编辑工作副本。它与产品仓库分开管理；是否建立独立 private Git 仓库由维护者决定。
- **只留在本机的生成物**：依赖目录、编译缓存、`dist/`、`test-results/`、日志和本地设置。用 `.gitignore` 排除，但忽略规则不会移除已提交的内容。
- **凭据**：密钥、签名证书、令牌和含真实凭据的 `.env` 不进入任何 Git 仓库。使用本机安全存储或托管平台的 secrets 设置。

计划中的本地总目录是 `Leaf/`（不设 Git 仓库），内含产品目录 `leaf-public/` 和私有工作目录 `leaf-work/`。计划中的 GitHub 仓库分别是公开的 `leaf-markdown` 与私有的 `leaf-work`；本地目录名不必与 GitHub 仓库名相同。这些是目标名称，迁移完成前不要把它们当作当前路径。

以后建立公开仓库后，让它成为 Leaf 产品代码的主仓库；私有工作空间保存不宜公开的过程材料。不要建立需要日常同步两份产品代码的特殊镜像流程。现有 private 仓库的历史含内部材料，不应直接改成 public；也不要擅自修改 remote。

## 一项工作如何完成

1. 从最新的稳定 `main` 开一条功能或修复分支。一次分支围绕一个可解释的目标；需要隔离实验时另开分支。
2. 开工前查看 Git 状态，保护已有未提交修改。开发中可以保存 checkpoint commit，提交信息说明目前做到哪一步；一次对话不必对应一次 commit。
3. 功能完成后，按功能检查改动和暂存内容。源码、测试、文档、资源可以在同一功能提交中配套出现；无关改动分开提交。不把个人资料或构建产物顺手提交。
4. 运行与改动相称的检查。普通改动至少运行 `npm run check`；界面行为补跑相关浏览器测试；桌面文件、输入或平台行为补做相应原生检查。浏览器和构建通过不等于安装版验收。
5. 通过 PR 检查后合入 `main`。一串只为临时存档的 checkpoint 可 squash；几个独立且有追溯价值的提交可保留。不要为了整齐改写现有有价值的历史。
6. 合入后确认 `main` 的自动检查通过。需要安装包时按发布流程构建，不把安装包或缓存提交进源码。

`main` 应表示当前可构建、已通过约定检查的产品基线。紧急修复也在分支上完成并回到 `main`。对未完成的工作保留在分支，不让主线长期处于已知损坏状态。

## 给协作 Agent

- 开始前读本文件、`README.md`、`docs/DEVELOPMENT.md` 和与任务相关的源码／测试；不要把旧过程记录当作现行事实。
- 先检查工作区、当前分支与用户已有修改。提交前检查暂存边界；只提交本任务的文件。
- 发现敏感资料时停止传播其内容，报告路径与风险，不把它复制到新仓库或提交中。
- 建分支、提交、合并和推送应遵照用户当前授权与阶段要求；不得自行公开仓库或改 remote。
