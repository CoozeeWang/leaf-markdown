# Leaf 开发与仓库工作方式

这份说明供 Leaf 的开发者使用。公开产品仓库是 `CoozeeWang/leaf-markdown`；目前处于 Beta 阶段。

## 哪些资料放在哪里

- **公开产品仓库 `leaf-markdown`**：源码、正式测试、必要资源、依赖锁文件、构建和打包配置、面向开发者的现行文档。被 Git 跟踪的内容应可以公开。
- **私有工作资料**：个人研发记录、过程性方案、内部验收材料和可编辑工作副本不提交到本仓库。
- **只留在本机的生成物**：依赖目录、编译缓存、`dist/`、`test-results/`、日志和本地设置。用 `.gitignore` 排除，但忽略规则不会移除已提交的内容。
- **凭据**：密钥、签名证书、令牌和含真实凭据的 `.env` 不进入任何 Git 仓库。使用本机安全存储或托管平台的 secrets 设置。

`leaf-markdown` 是 Leaf 产品代码的主仓库。个人工作目录的名称和组织方式由各位开发者自行决定。

## 一项工作如何完成

1. 从最新的稳定 `main` 开一条功能或修复分支。一次分支围绕一个可解释的目标；需要隔离实验时另开分支。
2. 开工前查看 Git 状态，保护已有未提交修改。开发中可以保存 checkpoint commit，提交信息说明目前做到哪一步；一次对话不必对应一次 commit。
3. 功能完成后，按功能检查改动和暂存内容。源码、测试、文档、资源可以在同一功能提交中配套出现；无关改动分开提交。不把个人资料或构建产物顺手提交。
4. 运行与改动相称的检查。普通改动至少运行 `npm run check`；界面行为补跑相关浏览器测试；桌面文件、输入或平台行为补做相应原生检查。浏览器和构建通过不等于安装版验收。
5. 通过 PR 检查后合入 `main`。一串只为临时存档的 checkpoint 可 squash；几个独立且有追溯价值的提交可保留。不要为了整齐改写现有有价值的历史。
6. 合入后确认 `main` 的自动检查通过。需要安装包时按发布流程构建，不把安装包或缓存提交进源码。

`main` 应表示当前可构建、已通过约定检查的产品基线。紧急修复也在分支上完成并回到 `main`。对未完成的工作保留在分支，不让主线长期处于已知损坏状态。

## Beta 版本号与内部测试构建

- 产品版本号（如 `0.4.0-beta.2`）标识一轮 Beta 基线，不单凭这个数字判断它已对外发布。日常修复 Issue、制作内部测试包或把测试包装到自己电脑继续试用，都不因此逐次升级 Beta 版本号。测试版靠应用「设置」中的构建标记识别具体源码提交与构建时间；交付和验收记录写明实际构建标记。内部测试包文件名包含源码提交号和平台，避免把不同构建误认成同一份。
- 准备通过 GitHub Releases 发布供别人下载的下一轮 Beta 时，先核对拟发布源码中已合入 `main` 的改动，以及 macOS、Windows、中文和英文各自的验证范围；若此前已有发布版，再与上一发布版比较。由维护者决定是否发布及新版本号。同一目标版本连续发布的 Beta 使用 `X.Y.Z-beta.N`，每发布一轮将 `N` 加一；若要改变 `X.Y.Z`，先明确本轮目标。未合入的测试分支和仅制作过测试包的修改不计入发布内容。
- 确定发布后、生成发布包前，同步更新 `package.json`、`package-lock.json`、`src-tauri/Cargo.toml`、`src-tauri/Cargo.lock` 和 `src-tauri/tauri.conf.json` 中的产品版本号。更新说明按实际合入的功能与修复及对应 Issue／PR 编写，不按内部构建号罗列。源码合入、内部包构建和本机安装均不等于已经发布；对外发布状态以 GitHub Releases 为准。
